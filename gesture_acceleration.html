Downscaler

Hardware-Accelerated Video Downscaler

To run the MediaPipe gesture recognition model efficiently on the Zynq Processing System, the 1080p camera feed must be downscaled to a 224x224 RGB format. Rather than relying on the ARM CPU for image processing, we implemented a custom RTL downscaler in the FPGA fabric to handle this step prior to memory storage.

Hardware Flow Diagram

Here we can see the abstracted view of the hardware/PL design. Generally, A MIPI CSI camera (PCAM5) clocked at 200MHz feeds into a demosaic module (Vivado IP) converting the raw bayer data into standard RGB. Here, the data stream splits. One stream is grayscaled, while the other stream remains RGB. The RGB stream is then fed into the downscaler (detailed below)

  Architecture and Data Flow The downscaler sits directly in the camera's AXI-Stream pipeline. This direct-stream approach bypasses the DDR memory entirely for the 1080p input. Input: Raw 1080p video streamed directly from the camera sensor at a ~75MHz pixel clock. Output: A 224x224 RGB frame (~150 KB) written to a /dev/shm RAM disk via a Video Direct Memory Access (VDMA) block. Logic: The module utilizes a parameterizable adder tree for the downscaling math, requiring zero DSP slices. Additionally, color channel correction (converting the camera's output to the RGB format expected by MediaPipe) is handled entirely through wire routing on the AXI bus, requiring zero logic gates and adding zero latency. Processing and Latency The downscaler's fabric is clocked at 200MHz. At this speed, the theoretical compute time for the RTL logic to process the data is roughly 70 µs. However, because the system is I/O-bound by the camera's live ~75MHz feed, the computation is effectively hidden within the camera's natural exposure and readout time. To further reduce latency, the downscaler implements a 3/4 frame crop. Since the user's hand gestures naturally occur in the upper portion of the camera's view, the module stops processing and fires its final tlast signal after reading 75% of the 1080p frame. Software vs. Hardware Comparison This hardware implementation minimizes both total latency and CPU utilization. Hardware Pipeline: With the 3/4 early-exit crop, the downscaled 224x224 frame is fully processed and committed to memory in approximately 25 ms—before the camera has even finished capturing the bottom 25% of the frame. Estimated Software Pipeline: A standard software approach would require waiting for the full 1080p frame to buffer into RAM (~33.3 ms at 30 FPS), followed by a CPU-bound resize operation (estimated at ~30 ms under load). This would result in a total latency of roughly ~63 ms. By handling the resizing and color swapping inline as the pixels arrive, we eliminate the preprocessing overhead, allowing the Zynq's ARM cores to dedicate their full resources to running the AI inference.
